# Анализ архитектуры взаимодействия сервисов и риски при росте числа страховых компаний

## Исходные данные (из условия задания)
1. `ins-product-aggregator` синхронно опрашивает API всех страховых компаний (СК) при каждом вызове, агрегирует данные и возвращает результат в рамках того же запроса.
2. `core-app` хранит локальную реплику продуктов и обновляет её через REST-запрос к агрегатору раз в 15 минут.
3. `ins-comp-settlement` хранит локальную реплику продуктов и обновляет её через REST-запрос к агрегатору раз в сутки (ночью).
4. `ins-comp-settlement` раз в сутки синхронно запрашивает у `core-app` все оформленные за день страховки через REST API.
5. Периодически возникают ошибки взаимодействия из-за задержек ответов или сбоев API страховых компаний.
6. Планируется увеличение количества СК с 5 до 10.

## Таблица проблем и рисков

| Проблема                                                                                                                                                                                                                                  | Вероятность сейчас | Вероятность при росте до 10 СК | Оценка риска | Решение                                                                                                                                                                                                                  |
|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|--------------------|--------------------------------|--------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **1. Блокировка при сбое внешних API** Агрегатор синхронно опрашивает все СК; задержка или ошибка одной СК задерживает весь ответ. `core-app` и `ins-comp-settlement` не получают обновлений.                                             | Средняя            | Высокая                        | Высокий      | Агрегатор публикует события `ProductCatalogUpdated` в Kafka сразу по мере получения данных от каждой СК (частичные обновления). Потребители подписываются на топик и обновляют реплики асинхронно.                       |
| **2. Устаревание данных в `core-app`** Локальная реплика обновляется раз в 15 минут. При росте числа СК и частоты изменений тарифов 15-минутное окно становится критичным.                                                                | Средняя            | Высокая                        | Средний      | `core-app` подписывается на `product-updates` и обновляет реплику в реальном времени (секунды), а не по расписанию.                                                                                                      |
| **3. Риск потери данных при ночной выгрузке страховок** `ins-comp-settlement` забирает все оформленные за день страховки одним синхронным REST-запросом. При росте объёма данных возможны таймауты и потеря батча. Нет гарантии доставки. | Средняя            | Высокая                        | Высокий      | Внедрить Transactional Outbox в `core-app`: событие `InsuranceIssued` записывается в одной транзакции с полисом и асинхронно публикуется в Kafka. `ins-comp-settlement` потребляет события инкрементально, идемпотентно. |
| **4. Жёсткая связность и каскадные отказы** Все три сервиса связаны синхронными HTTP-вызовами. Сбой в агрегаторе блокирует обновление реплик в обоих потребителях; сбой в `core-app` блокирует формирование реестра.                      | Средняя            | Высокая                        | Высокий      | Kafka выступает буфером: сообщения накапливаются, даже если потребитель временно недоступен. Сервисы работают независимо.                                                                                                |
| **5. Нелинейный рост нагрузки на агрегатор** При 10 СК время обработки каждого синхронного запроса возрастёт. Агрегатор становится точкой отказа в моменты пиковых pull-запросов.                                                         | Низкая             | Средняя                        | Средний      | Агрегатор больше не вызывается синхронно. Он фоново опрашивает СК и публикует события. Потребители читают из Kafka, не нагружая агрегатор напрямую.                                                                      |
| **6. Отсутствие гарантий доставки при сбоях сети** Ночной запрос `ins-comp-settlement` к `core-app` не имеет механизма повторных попыток и идемпотентности. При ошибке данные могут быть потеряны или продублированы.                     | Средняя            | Высокая                        | Высокий      | Transactional Outbox + идемпотентная обработка в settlement (по `policy_id`). At-least-once с дедупликацией.                                                                                                             |

## Риски при росте до 10 страховых компаний

| Риск                                          | Последствие                                                                                                    |
|-----------------------------------------------|----------------------------------------------------------------------------------------------------------------|
| Увеличение p99 латентности агрегатора         | Обновление реплик в `core-app` начнёт превышать 15-минутный интервал; возможны таймауты и пропуски обновлений. |
| Рост вероятности частичных сбоев внешних API  | Локальные реплики будут регулярно содержать неполные или устаревшие данные.                                    |
| Увеличение объёма суточной выгрузки страховок | Ночной REST-запрос `ins-comp-settlement` станет нестабильным; риск потери финансовых данных.                   |
| Невозможность уменьшить интервал обновления   | При синхронном подходе уменьшение интервала опроса только ухудшит ситуацию с таймаутами.                       |
| Каскадные отказы при пиковой нагрузке         | Сбой одной СК может заблокировать обновление данных для всех потребителей.                                     |
